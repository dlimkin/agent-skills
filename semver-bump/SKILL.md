# Semver Bump

Update the requested release unit to a valid target version with the smallest
correct diff. This skill edits version data only. It does not publish, push,
create tags, run a release, or create a release commit unless the user
explicitly authorizes that larger scope.

## 1. Establish the release unit and scope

Before editing, determine what is being released:

- a single application, service, library, plugin, image, chart, or package;
- one package in a monorepo, where packages may be independently versioned;
- several packages that the repository intentionally releases in lockstep; or
- a synchronized product with an explicitly documented shared version.

Use the user's explicit target and scope. A request for a root application does
not implicitly include sibling packages, examples, fixtures, vendored code, or
templates. Do not infer a major or minor bump from a vague request or from
changes alone; use repository policy or ask when the intended target is not
specified. If the user explicitly gives a target, do not silently replace it
with a different one.

## 2. Map version roles before changing anything

Search the relevant repository scope broadly for case and format variants such
as `version`, `VERSION`, `Version`, and the current value. Classify each match
before editing it:

1. **Authoritative literal** — the source of truth that must change.
2. **Explicit mirror** — a manually maintained copy that repository workflow
   says tracks the release unit; change it with the source of truth.
3. **Derived value** — computed by reading another file, command, Git state,
   or an environment variable; change its input, never the computation.
4. **Generated metadata** — regenerated by a build or release tool; update it
   only through the repository's documented generation path when it is in
   scope.
5. **Independent field** — a version-like value for another artifact or
   compatibility scheme; leave it alone unless the release workflow explicitly
   maps it to this release.

Trace scripts, build configuration, and Git-derived version functions far
enough to identify the real source. Do not forge a missing literal merely to
make a search look consistent, and do not create a tag to satisfy a dynamic
version source. Never perform a blind global replacement or assume every
version-looking field is the same SemVer.

File names such as `package.json`, `Cargo.toml`, `pyproject.toml`, `*.csproj`,
`pubspec.yaml`, `Chart.yaml`, `VERSION`, `Makefile`, Gradle files, plist files,
and CI manifests are non-exhaustive hints, not a project-type requirement.

Preserve unrelated dependency constraints, historical changelogs, fixtures,
vendor content, and template defaults. Change dependency references only when
the repository's release workflow explicitly requires an in-scope package
reference to move with this release.

Special cases require the repository's mapping, not guesswork:

- A lockfile's own package metadata may be an explicit mirror. Update it with
  the existing no-release tooling or the smallest supported edit, without
  resolving dependencies, changing unrelated lock entries, or running
  lifecycle release scripts.
- Assembly/file ABI versions, Android integer `versionCode` values, and
  Flutter `+build` values are not identical SemVer copies. Change or project
  them only according to documented compatibility and monotonicity rules.
- A Helm `Chart.yaml` `version` and `appVersion` represent different things;
  do not synchronize them unless the chart workflow says so.

## 3. Validate and choose the target

Read the current version from the authoritative source before calculating a
bump; never guess a starting point. If declarations disagree, identify the
authority from repository configuration or ask when it cannot be established.
For an explicit target, synchronize the mapped locations to that target.

Use strict SemVer parsing for an explicit target before editing. SemVer core
versions contain three non-negative integer components without leading zeroes.
Prerelease identifiers are dot-separated and nonempty, contain only ASCII
letters, digits, or hyphens, and numeric identifiers have no leading zeroes.
Build identifiers are also dot-separated and use the same characters; numeric
build identifiers may have leading zeroes. Build metadata does not affect
precedence; a prerelease has lower precedence than its corresponding
final version. See the [SemVer specification](https://semver.org/).

For a component bump, increment the requested component and reset lower
components: patch resets nothing, minor resets patch, and major resets minor
and patch. Keep or remove prerelease/build metadata only according to the
explicit target and repository policy.

The words `patch`, `minor`, and `major` do not define how tooling moves from a
prerelease. SemVer does not prescribe that policy. Read the repository/tool
behavior and state the chosen result. If the user means “finalize this
prerelease”, do not accidentally advance `1.2.3-rc.1` to `1.2.4`; ask only
when that intent is genuinely ambiguous. Do not invent prerelease channels.

Compare old and new versions and call out same-version synchronization,
intentional downgrades, or a non-increasing target. A deliberate downgrade is
allowed when explicitly requested; an accidental non-increase requires
clarification. A leading `v` belongs to a tag or display convention, not the
SemVer core value, unless a repository field explicitly documents another
format.

## 4. Edit only the mapped literals

Apply the target to every authoritative literal and documented mirror for the
release unit. Leave derived lines untouched and preserve formatting, ordering,
comments, and unrelated values. When multiple release units exist, report the
ones intentionally left independent.

Do not edit generated files by hand unless the repository treats them as
tracked, authoritative release metadata and documents that workflow. Do not
resolve dependencies just to refresh a lockfile, and do not invoke scripts
whose lifecycle would publish, tag, push, or otherwise perform a release.

## 5. Verify the result

Use checks appropriate to the selected files and repository tooling:

- parse structured manifests (JSON, YAML, TOML, XML, plist, or equivalent);
- confirm every mapped literal and mirror resolves to the target;
- resolve derived values and confirm they produce the target without editing
  their source expression;
- validate ecosystem projections such as integer codes or chart/app mappings;
- search for the old version with fixed-string matching, then classify every
  remaining occurrence rather than demanding zero matches globally;
- run a cheap relevant build, lint, or repository validation when available;
- inspect the final diff for minimal scope and accidental dependency churn.

Do not call the bump complete without fresh command output from the checks you
ran. If a check fails, report the failure and do not imply that the version was
successfully updated.

## Report

Report:

- release unit and old → new version;
- authoritative files and explicit mirrors edited;
- deliberately independent fields or files left unchanged, with their reason;
- validation commands and their results;
- any unresolved ambiguity or remaining failure.
